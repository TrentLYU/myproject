# 反馈与改进（Feedback & Iteration）

> **报告补充材料 d)**：Feedbacks collected and decision-making（reasons and discussion）
> 方法论依据：V3 课件（反馈后台 / 发布 / 密钥安全 / 「本地成功 ≠ 线上成功」）、V4 课件（Feedback → Decision → Iteration → Verification · 七分类 · Impact × Effort · Accept / Modify / Delay / Reject · 回归测试）

---

## 一、反馈闭环总览

本项目完整走通了 V4 课件的闭环：

```
Build 构建(v0~v2.1.7) → Polish 打磨(各代迭代) → Publish 发布(v2.2.0 起 GitHub Pages)
→ Collect Feedback 收集(云端反馈墙 + 访客反馈 + 多端自测) → Decide 判断(分类/排序/决策表)
→ Iterate 迭代(v2.2.1 补丁 + 4 次线上提交) → Verify 验证(回归测试)
```

一句贯穿全程的关键认知（V4 课件）：**Good iteration is not make more changes. Good iteration is make better decisions.** —— 9 天 23 版的节奏很快，但 V4 阶段的每一处改动都不是「顺手多加点」，而是先有反馈证据、再有问题定义、最后才有代码。

## 二、反馈渠道建设（课程 V3 阶段成果）

### 2.1 反馈功能的三步演进

| 版本 | 形态 | 数据流向 |
| --- | --- | --- |
| v2.1.8（09-19） | 五星评分反馈墙 1.0 | 访客浏览器 localStorage（仅本机可见）——静态站点无后端时的过渡方案 |
| v2.2.0（09-20） | 发布到 GitHub Pages | 真实访客开始通过公开网址访问并留下反馈 |
| v2.2.1（09-22） | **Supabase 云端反馈墙 2.0** | 浏览器 → Supabase（PostgreSQL `feedback` 表），所有访客实时共享，20 秒自动拉取 |

### 2.2 表单设计（字段刻意做减法）

按 V3 课件「字段越少，越有人愿意填」原则，最终字段：昵称（选填，可匿名）/ 五星评分（App Store 同款悬停预览）/ 建议正文（必填，500 字上限）。发布按钮在「打分 + 写完建议」前保持禁用，防误发。

### 2.3 架构与安全要点（V3 课件对照）

- **数据流方向**：浏览器 → Supabase 后台（GitHub Pages 只发文件，绝不替访客写数据库）；前端使用 publishable key，**高权限 secret key 从未进入前端 / 仓库 / 课件**。
- **凭据治理**：早期硬编码 Key 在归档时全部脱敏（`sk-REDACTED`，10 文件 11 处），全仓正则扫描零残留。
- **XSS 防护**：反馈正文一律 `textContent` 渲染，杜绝 HTML 注入。
- **失败体验**：云端发布失败提示可重试，输入内容不丢失。
- **验收方式**：按课件标准「不能只看提交成功提示」——带唯一标记测试提交后，回到 Supabase Table Editor 找到同一条记录（字段完整、时间正确）才算通过。

### 2.4 一个有意为之的设计偏离（决策讨论）

V3 课件建议「反馈不公开、仅主人后台可见」，本项目选择了**公开反馈墙**（所有访客可看到彼此的评分与建议）。理由：① 个人主页的反馈天然偏「留言板」属性，公示能形成社区感与真实感；② 公开反馈本身就是网站可信度的一部分。风险与对策：恶意刷评与滥用——当前已做字数限制 + XSS 防护，**限流/验证码列为暂缓项**（见决策表 F11），与课件「长期公开使用需额外防滥用」的提醒一致，将在访客量真正增长后实施。

## 四、从反馈到问题：Problem ≠ Suggested Solution（V4 课件方法）

访客擅长说「哪里不舒服」，但其「怎么改」的方案不一定最好。两条典型翻译：

**示例一（F4 教育经历）**
- 访客说法（Solution）：「把时间倒过来排吧，从大学往回排。」
- 背后问题（Problem）：时间线方向与阅读习惯冲突——访客期待自上而下读出「成长叙事」，倒序却先给结果后给起点。
- 最终修改没有照搬「倒过来」的细节建议，而是确立「按成长正序自上而下」的叙事原则：九一小学 → 常青藤中学 → 山西大学附属中学 → 天津大学。

**示例二（F3 PDF 自动下载）**
- 现象说法：「你们的 PDF 下载太烦了。」
- 背后问题：页面加载即 iframe 预载 PDF，而部分移动浏览器的处理方式是直接下载——问题根源在「自动加载」，不在「PDF 本身」。
- 修改：移除自动加载，改为访客主动点击 + 确认弹窗（HEAD 探测真实大小）——保留了 PDF 能力，消除了打扰。

## 五、优先级排序：Impact × Effort（V4 课件四象限）

| 象限 | 对应反馈 | 处理建议 | 实际处理 |
| --- | --- | --- | --- |
| **High Impact + Low Effort** | F5 按钮符号消失、F6 国旗空白、F7 VR 404、F9 音乐条遮挡、F2 邮箱溢出、F10 iPad 弹窗 | 优先修改 | 全部当轮修复 ✅ |
| **High Impact + High Effort** | F3 PDF 打扰、F4 教育经历叙事、F8 语言弹窗打扰 | 认真评估、规划后再做 | 当轮完成（F8 整体重构为底部抽屉）✅ |
| **Low Impact + Low Effort** | F1 手机端文字居中 | 有时间再优化 | 顺手完成（与 F9 同批）✅ |
| **Low Impact + High Effort** | F11 反馈墙防滥用（限流/验证码） | 通常暂时不做 | 暂缓，设为访客量增长后的触发项 ⏸ |

排序依据补充：网站目标定义为「帮助访客在 30 秒内了解我是谁、做过什么、如何联系我」（V4 课件 Prompt 3 的目标锚定）。凡直接影响该目标的（F4 内容表达、F7 功能错误）优先级上调；纯偏好类不影响目标，下调。

## 六、决策记录表（Accept / Modify / Delay / Reject）

> 对应 V4 课件「Feedback Decision Table：说明你怎么判断每条反馈」。

| 编号 | 决策 | 理由（reasons） |
| --- | --- | --- |
| F1 | **Accept** | 移动端是主要访问场景之一，成本极低 |
| F2 | **Accept（立即）** | 功能性视觉缺陷，一行样式修复 |
| F3 | **Modify（变通）** | 不删除 PDF 功能（它是项目展示核心），只移除「自动」行为，改主动确认 |
| F4 | **Accept** | 直接影响主页核心叙事（成长故事线） |
| F5 | **Accept（立即）** | 功能错误，课件定义的最高优先级 |
| F6 | **Accept（立即）** | 兼容性缺陷，四处统一修复 |
| F7 | **Accept（立即）** | 链接失效 = 功能错误；顺带暴露「本地成功 ≠ 线上成功」的部署差异（全角括号 + 路径前缀） |
| F8 | **Accept（重构）** | 首因效应问题——第一印象被弹窗打断，值得整体重做而非小修 |
| F9 | **Accept** | 内容被遮挡属于可用性问题，非偏好 |
| F10 | **Accept** | 一行 `min()` 限宽，成本极低 |
| F11 | **Delay** | 当前访客规模下滥用风险低；实现成本（验证码/限流）不匹配收益；设触发条件「单日反馈异常增长」再启动 |
| — | **Reject（不采纳）**：深色主题 | v1.3.3pro 曾做深色主题探索，最终不纳入主线：① 与页面「学术 + 清新」定位不符；② 需三语 × 三端双倍维护成本；③ 属个人偏好类，不影响网站目标。**Reject ≠ Ignore**——保留评估记录（本文档），将来若多数访客明确提出再重新评估 |

**冲突处理示例**（V4 课件场景）：有访客喜欢深色氛围，也有访客提到浅色下文字更易读——前者是 Preference（偏好），后者是 Usability（可用性）→ **可用性优先**，维持浅色主设计。

## 七、假设式迭代完整案例（对 F8 / F4 的处理）

> V4 课件：不要「User said X → AI changes X」，要「I think the problem is X → I change Y → I expect Z → I test it」。

| 环节 | 内容 |
| --- | --- |
| **Feedback 反馈** | F8：页面刚加载完成就弹出居中语言选择框，第一印象被打断；F4：教育经历倒序，成长感缺失 |
| **Interpretation 我的解读** | 首屏渲染与语言选择「两个第一印象同时发生」互相争抢；时间线方向与「自上而下 = 从过去到现在」的阅读直觉冲突 |
| **Change 我的修改** | 语言选择重构为底部抽屉（0.6s 延迟弹出 + iOS 把手 + 安全区适配 + 竞态保护：等待期间已手动切换则不再打扰）；教育经历改成长正序 |
| **Expected result 预期结果** | 访客先看清首页再被温和地询问语言；教育经历读出「一路成长」的叙事 |
| **Verification 验证** | 语言弹窗 9 项结构检查全过；CSS 花括号 512 对平衡；i18n.js 语法校验通过；对 history/ 归档页面向后兼容（无弹窗元素自动跳过）；真机复查叙事顺序 |

## 八、回归测试（Regression Testing）

V4 课件强调「AI says done ≠ task is finished」。本项目的制度化做法是：**每版必测、先仿真后上线、修改必回归**。V4 阶段实际执行的回归清单（对应课件六项）：

| 检查项 | 怎么测 | 结果 |
| --- | --- | --- |
| 桌面布局 | 电脑打开逐屏滚动，查错位/重叠/溢出 | ✅ 无异常 |
| 手机布局（≤640px） | iPhone 实机逐屏滚动 | ✅ 文字无需放大即可读（F1 修复后复核） |
| 导航与按钮 | 逐个点击全部导航项与按钮 | ✅ 均达正确位置（含新增演进史入口） |
| 图片与链接 | 逐个打开项目/证书/照片 | ✅ 无失效（F7 两处 iframe 修复后 HTTP 200 复核） |
| 反馈表单 | 实际提交一条带标记反馈 | ✅ 写入 Supabase，Table Editor 可查 |
| 加载速度 | 刷新观察首屏 | ✅ 无长时间等待（未引入重依赖的直接收益） |
| 自动化回归 | check-221（48/48）、sim-globe（33/33）、sim-i18n（18/18）、sim-feedback（22/22）、三语问答（zh 20 / en 7 / tw 6） | ✅ 全过 |
| 版本回退能力 | 确认 23 个归档版本线上可访问 | ✅ history/ 全部 HTTP 200 |

**一个真实的回归教训（P8）**：v2.1.9 视频功能上线当晚自测发现「点击任意处关闭灯箱」的事件冒泡会吃掉视频控件点击——功能「AI 说做好了」但真机不可用。当即修复（仅点遮罩/大图关闭）并补 11 项视频仿真用例。这件事直接促成了此后「每版必附仿真验证记录」的制度化（CHANGELOG 可查）。

## 十、反思（V4 课件五问）

1. **你收到了什么反馈？** 十余条，集中在移动端体验、细节缺陷与内容叙事（F1–F11），另有深色主题等偏好类建议。
2. **你采纳了哪些？** F1–F10 全部处理（九项 Accept、F3 变通为主动确认）。
3. **哪些没有采纳？** 深色主题（Reject，理由见决策表）；反馈墙防滥用（Delay，设触发条件）。
4. **为什么这样决定？** 判断依据始终是四条：网站目标（30 秒认识我）、是否影响可用性、出现频率与可复现性、改动成本（Impact × Effort）。偏好类反馈听取但不盲从——**反馈是参考证据，不是每条都必须照做**。
5. **这一轮之后发生了什么变化？** 除上表可见的变化外，更重要的变化是工作方式：从「想到什么加什么」变为「证据 → 问题定义 → 假设 → 修改 → 回归」的决策流程，并沉淀为 CHANGELOG 与仿真验证制度。这正是课程想传达的：**A better product does not come from more prompts. It comes from better decisions.**
